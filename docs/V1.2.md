# V1.2 forward experiment

## Architecture and deliberate defaults

One process, one OS lock per database, one CoinGecko collection per scan. The
unchanged `intelligence/statistical.py` remains the V1.1 detector. Its candidate
rows, AI request construction, outcomes and scoring thresholds remain intact.
Both modes use the maintained stablecoin list, now including `usd1-wlfi`, `usd1`
and `bfusd`. This explicit exclusion correction changes eligibility for these
assets; do not combine the before/after cohorts without recording that change.

V1.1 runs first. Its news requests are cached with their actual observation
timestamps. V1.2 then polls a bounded rotating set of assets using the existing
Google News RSS collector, without requiring a market anomaly. One normalized
social collector batch serves the whole tracked universe. A failure is recorded
without aborting the continuous loop. Experimental outcome failures are isolated
from V1.1 scoring/AI. All assessments still use the existing strict Pydantic schema.

The default remains V1.1. `--detector all` explicitly enables both; `v12.enabled:
true` enables both when the CLI mode is omitted. V1.2 AI/alerts remain disabled
until explicitly enabled. This collects useful deterministic comparisons without
extra OpenAI spending. No trading, exchange microstructure or whale signals exist.

The complete `v12` section is included in `config.yaml`; defaults are validated in
`experiment_config.py`. Unknown keys, unsupported providers and invalid numeric
settings fail at startup. Configuration snapshots and hashes exclude environment
variables.

credentials were changed. `.env.example` documents the social integration gap.

## Social provider status and integration contract

There is **no production social provider**. Setting `enabled: true` with `provider:
none` still reports unavailable, never simulated activity. The deterministic
fixture provider can only be injected by code in tests; configuration rejects it.
Before testing the social hypothesis, choose a licensed API that provides historical
interval counts and implement its `SocialCollector.collect(assets, now)` adapter
and factory selection. Add provider credentials only through environment variables.
Provider pricing/rate limits and asset mapping must be reviewed during that integration.

Each validated observation maps to a CoinGecko ID and a source/community, with
an aligned, completed, non-overlapping 5-minute UTC bucket. Mention counts are
interval counts, not rolling totals. Optional author count, engagement, sentiment,
duplicate fraction and top-author fraction remain null when unavailable. Provider
metadata is limited to community and descriptions of duplicate/concentration methods;
raw credential-bearing responses are not persisted. Duplicate buckets are immutable.
Corrections/revisions are not supported in this first adapter contract.

`observed_ts` records receipt, separately from the bucket's event times. Features
use only received data at the evidence cutoff. The latest 5m/15m/1h counts require
complete buckets across the current source set. Missing buckets never imply zero.
The preceding baseline must have the configured coverage and enough windows.
Changes in source coverage therefore cannot create a simple count spike.

Acceleration is the latest three buckets' mean count divided by the mean of the
asset's own baseline buckets. Author and engagement acceleration use the same
method. Authors are unique **within each provider bucket**, not deduplicated across
the entire hour. Sentiment change is a difference of supplied means. Zero baseline
is `zero_baseline`, not infinite acceleration. A ratio of four saturates each
component: mentions 60 points, authors 25, engagement 15. Missing components score
zero and remain visibly missing. Sentiment alone adds no points. Cross-source
spread and available promotion-risk metadata are persisted. Unknown manipulation
metrics cannot establish that a signal is organic.

## News and deterministic groups

News labels are conservative headline regex hypotheses, not fact verification.
Supported categories: exchange listing, partnership, product/project launch,
protocol upgrade, hack/security incident, regulatory event, funding/investment,
tokenomics event, influencer/high-profile mention and unknown. `other` remains an
available future semantic category; the current classifier uses unknown for unmatched
headlines. Relevance requires the asset's full name in the headline; ambiguous bare
tickers are not enough. This intentionally misses some genuine ticker-only news.

First observation is immutable. Publication time stays null when unparseable. Future
publications and known publications older than the age limit are excluded. Exact
normalized headline duplicates count once; publisher suffixes are removed. Syndication
does not renew a headline's original novelty clock. Different
headlines about the same event may still count separately. Source quality is unknown
unless explicitly configured trusted. Distinct publishers **do not prove independent
confirmation**: that analytical field stays null. No invented verification count.

A headline earns 15 points, plus 20 for a recognized catalyst, plus 10 for a configured
trusted source. Multiply by novelty (linear decay from first observation to zero over
6h); halve if publication time is missing. Sum unique-headline scores, capped at 100.

Every fetched asset has an experimental evaluation for each enabled detector:

- V1.1: `market_only`, with exact original evaluation ID and unchanged market score.
- V1.2: `social_only` or `news_only` when that upstream component alone qualifies.
- Both upstream components: `social_news`; score is their mean.
- Both upstream components plus a qualifying market score: `market_social_news`;
  score is 40% social + 40% news + 20% market.
- Neither upstream component: `no_upstream_signal`, retained as rejected control.

For the single-upstream groups, the ranking uses only that upstream score even if
market evidence is also present; market components remain inspectable. Shared V1.1
liquidity/valid-price/maximum-24h-move filters still gate V1.2. Consequently this version
does not search low-liquidity assets excluded by V1.1. Groups are **descriptive strata,
not randomized arms or four independent ablation detectors**. Compare all groups while
controlling for overlapping assets, market regime and repeated episodes.

## Migration and durable data

Schema version 2 applies only on a future explicitly started upgraded scanner/migration.
Development and tests use temporary databases; the production DB is not migrated here.
Before any pending migration the existing SQLite online-backup mechanism creates
`crypto_radar.db.before-schema-2-<UTC timestamp>.bak`. Pending v1/v2 statements and
schema-version updates commit together with `BEGIN IMMEDIATE`; any failure rolls back.
No existing table is dropped or recreated. Migrations are idempotent.

New tables: `social_observations`, `social_features`, `news_evidence`, `collector_runs`,
`research_episodes`, `experiment_evaluations`, `evaluation_news`, `benchmark_context`,
`benchmark_members`, `experiment_outcomes`, `benchmark_outcomes`, `v12_ai_calls`.
Assessments add nullable `experiment_evaluation_id` and `v12_ai_call_id`; alert events
add nullable `research_episode_id`. New analytical indexes and views
`experiment_lead_times` / `experiment_ai_usage` support analysis. Important numeric
features are columns; JSON retains full component detail/configuration/dossiers.

Legacy records are not retroactively assigned fabricated social evidence or chronology.
The upgraded V1.1 mode writes supplemental forward measurements as well as its unchanged
legacy rows. Do not run the old V1.1 binary against schema 2 (its version guard rejects
it). Use `--detector v11` in the upgraded code for the control and rollback of detector
mode; reverting schema requires a separately planned backup restore, never table deletion.

## Outcomes, market regime and chronology

All valid experimental evaluations, including non-AI/rejected/suppressed controls, get
1/3/6/12/24-hour outcome targets. Stablecoin/invalid/excluded rows remain auditable but
have no fabricated outcome price. Starting price and targets use the market observation
timestamp; detection and evidence cutoff are separate columns. News collection can make
detection a few minutes later than the price anchor; account for this lag in comparisons.

The earliest stored valid price at or after target is used. Actual time and lateness
are persisted; late observations remain late. Each BTC/ETH return uses exactly the
candidate's starting and ending collection timestamps. Missing endpoints yield null,
not a different time window. Excess return is candidate return minus benchmark return
in **percentage points**. Broad return is a simple initial equal-weight basket of other
tracked non-stablecoins. Membership and starting prices are frozen per scan, shared across
evaluations. Every member must have the exact endpoint and the minimum basket size must
be met; otherwise the broad return is null. This avoids silent survivor reweighting.
It is a tracked-universe benchmark, not the entire cryptocurrency market.

Research episodes span both detectors and use 24h without a qualifying signal to reset.
Continuous observations are required; downtime does not create independent episodes.
Persistent activity may conservatively keep one episode for many days. The five first
signal timestamps are set once and never backdated to publication/provider event time.
Raw news/social event and receipt times remain available for deeper chronology.

At episode creation, anchor to the latest valid price at or before detection minus one
hour, within ten minutes of that target; if unavailable use the current market price.
Freeze the anchor and +5% threshold. The significant-move timestamp is the earliest
stored crossing within 24h of that anchor, using only observations received by the
current scan. It can precede detection, correctly giving negative lead time. This is
an observed sampling crossing, not a claim about the exact exchange tick. Threshold,
window and definition version are stored per episode. `price_move_before_pct` records
anchor-to-detection market-price movement. An episode with no crossing is censored
until its observation window completes; gaps can make it unmeasurable.

## AI, alerts and operational limits

The existing global limits remain 50 attempted calls per UTC day and 8 per scan, counting
both AI tables (including failed/interrupted attempts). V1.2 adds a 10/day, 2/scan cap.
These are call limits, not dollar estimates; returned model/usage are stored for cost
analysis. V1.1 gets first opportunity each scan and retains its own cooldown. V1.2
suppresses same-scan overlap and respects the latest call from either detector. It can
override its own cooldown on a material score increase; unlike scales cannot establish
an increase over a V1.1 score. A later V1.1 candidate may still run after an earlier
V1.2-only call: preserving control AI policy is intentional. If V1.2 AI is enabled, shared
budget competition can affect which V1.1 candidates receive AI; deterministic candidates
and outcomes remain available regardless. Leave V1.2 AI off for the cleanest first cohort.

V1.2 dossiers explicitly separate market/news/social/regime evidence, timestamp and
configuration. No social or whale evidence is fabricated. Validated V1.2 assessments
link to experimental outcomes; they do not populate the legacy V1.1 outcome table.
Each alert channel uses the existing persistent delivery reservations and material-score
increase rule, with an additional shared research-episode guard. Uncertain delivery stays
deduplicated. V1.2-only mode maintains the legacy alert episode state using its eligibility.

Scan summaries include per-detector candidates and AI calls, overlap, V1.2-only candidates,
V1.2 suppressions, social/news status and errors. V1.2-only does **not** automatically mean
early: `v12_only_already_moved` and `v12_only_no_move_yet` distinguish observed chronology;
the latter is not a prediction that a future move will occur. Use persisted timestamps
for confirmed lead-time comparisons. Collector attempts are logged
in `collector_runs`; no recent headline is distinct from a failed or unpolled collector.

## Windows deployment and offline validation

No running task was restarted or changed during development. Do not launch a second
scanner beside the existing scheduled process; the shared DB lock rejects it.

After reviewing changes, stop the scheduled scanner (Task Scheduler → End) and run:

```powershell
Set-Location C:\crypto-radar
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -B -m crypto_radar.main --migrate-only
.\run_once.ps1 -Detector all
```

The last two commands intentionally modify the production DB when **you** execute them;
the scan uses live market/news services and V1.1 can send configured alerts. The test suite
uses temporary DBs and mocked paid APIs/alert delivery; the existing relay handshake test
opens loopback sockets but sends no message. No new packages are needed on Python 3.14.7.

Foreground continuous choices (choose one):

```powershell
.\run_forever.ps1 -Detector v11
.\run_forever.ps1 -Detector v12
.\run_forever.ps1 -Detector all
```

For combined boot startup, run in an administrator PowerShell after the manual check:

```powershell
.\install_startup_tasks.ps1 -Detector all
```

This existing installer restarts the scanner and relay and installs the single combined
scanner task. It does not create a second scanner or alter the weekly report task. Wrapper
scripts use the existing virtualenv, resolve their directory and propagate failures.

## Analysis and validation protocol

Use `eligible=1` for candidate cohorts, not merely successful AI assessments; use rejected
rows for controls. Link V1.1 AI through `v11_evaluation_id` → `assessments.evaluation_id`;
V1.2 links through `assessments.experiment_evaluation_id`. Group episodes first, then asset
and calendar period; assessments and five horizons are not independent experiments.

Read-only SQL examples (use a copied weekly DB):

```sql
SELECT COUNT(*) AS episodes,
       SUM(first_v11_candidate_ts IS NOT NULL) AS v11,
       SUM(first_v12_candidate_ts IS NOT NULL) AS v12,
       SUM(first_v11_candidate_ts IS NOT NULL AND first_v12_candidate_ts IS NOT NULL) AS both
FROM research_episodes;

SELECT coin_id, v12_before_v11_minutes, v12_before_move_minutes,
       first_social_anomaly_ts, first_market_anomaly_ts
FROM experiment_lead_times;

-- Descriptive only: reduce correlated rows to the first detection per episode/group
-- before inferential comparisons. Do not claim significance from this raw summary.
SELECT e.signal_version,e.experiment_group,o.horizon_hours,COUNT(*) AS observations,
       AVG(o.return_pct),AVG(o.excess_btc_pct),AVG(o.excess_eth_pct)
FROM experiment_evaluations e JOIN experiment_outcomes o ON e.id=o.evaluation_id
WHERE e.eligible=1 AND o.timing_status='within_tolerance'
GROUP BY e.signal_version,e.experiment_group,o.horizon_hours;

SELECT signal_version,budget_date,status,COUNT(*) FROM experiment_ai_usage
GROUP BY signal_version,budget_date,status;
```

Define success before evaluation, for example both reaching +5% by 6h and achieving
positive excess BTC return at the 6h endpoint; define a false positive as an eligible
signal that fails that prespecified success rule in a complete window. Distinguish
endpoint return from any-time
threshold crossings, and exclude incomplete/late windows. This release stores measurements
and analysis primitives; it does not deliver a calibrated success probability or automatic
statistical report. Social-vs-market ordering is not testable until real social data exists.

**First 24h:** verify a migration backup, schema 2 and no lost legacy records; one active
scanner; both detector counts; unavailable social clearly reported; rotating news coverage;
bounded scan duration; V1.2 AI count zero by default; no duplicate alerts; expanding pending
then measured horizons; exact BTC/ETH timestamps; reasonable missing/late rates; disk growth.
Every valid coin gets two forward measurement cohorts in combined mode: at 100 coins and
5-minute scans this can create about 288,000 horizon rows/day. Plan disk capacity and use
copied databases for heavy analysis. No automatic pruning deletes research data.

**Week 1:** engineering/data-quality validation. Fix corruption, invalid features or
collection failures, record changes and start a fresh clean cohort after material fixes.
**Weeks 2–4:** avoid aggressive tuning. Freeze scoring, thresholds, source mappings,
universe selection, horizons/tolerance, episode/move definitions, AI model/prompt and budgets.
Record unavoidable changes as new configuration/version cohorts. Do not deploy a new social
provider mid-cohort and describe it as the same experiment.

At approximately four weeks **and preferably ~500 reasonably independent episodes**, make
the first serious comparison, accounting for regime, selection and repeated assets. Continue
8–12 weeks before strong conclusions. Hundreds of assessments of a few ongoing events are
not hundreds of independent trials. Versioned evidence interfaces leave room for future
exchange/on-chain signals; none of the later trading roadmap is implemented here.
